# Планировщик приёмов: основа собственного движка

Собственный движок должен уметь, получив настоящий TLS ClientHello и описание приёма, ответить на вопрос «какие пакеты и в каком порядке отправить».
Эта часть не зависит ни от сети, ни от драйвера, поэтому её можно проверять где угодно. Она и есть первый готовый «кирпич».

## Что моделируется

| Приём | Что делает планировщик |
|---|---|
| `fake` | добавляет в начало поддельный пакет: сколько повторов (`dpi-desync-repeats`, по умолчанию 1) и какой длины (из файла `dpi-desync-fake-tls`, 0 если встроенный) |
| `multisplit` | режет данные по позициям `dpi-desync-split-pos`, отправляет сегменты по возрастанию смещения |
| `multidisorder` | то же, но сегменты идут в обратном порядке |
| `dpi-desync-split-seqovl` | у первого сегмента (смещение 0) указывается перекрытие в байтах, если пакет действительно разрезан |

Позиции разреза: число (смещение от начала), а также `host` (начало имени сайта), `endhost` (конец имени), `midsld` (середина домена второго уровня:
для `www.google.com` это середина слова `google`), с поправкой `+N` или `-N`. Позиции вне пакета отбрасываются, повторы убираются, список сортируется.

Всё остальное (`hostfakesplit`, `fakedsplit`, маркер `sniext`, `method` и другие) планировщик не моделирует и **явно перечисляет** в результате как неподдерживаемое.
Определения позиций здесь описаны так, как их понимает NORMA; в деталях они могут отличаться от `winws`, поэтому план это пояснение и основа для проверок, а не точная копия того, что делает `winws`.

## Строгий разбор ClientHello

Планировщик находит имя сайта строгим разбором: каждая длина проверяется относительно границы своей структуры, а не всего массива.
Запись TLS должна целиком лежать в данных; сообщение ClientHello должно занимать запись ровно (без лишних байт); список расширений заканчивается ровно на конце сообщения;
каждое расширение целиком внутри списка; в `server_name` список имён занимает всё расширение, имя одно (тип host_name), его длина не равна нулю и согласована со списком;
повтор расширения `server_name` запрещён. При любой несогласованности результат без SNI, а не «лучшее предположение».

Золотой файл содержит кроме обычных образцов искажённые: обрезанные в нескольких местах, с длиной записи, сообщения, списка расширений, расширения, списка имён и имени, увеличенной и уменьшенной на единицу
или выходящей за пределы, с неверным типом имени, нулевой длиной имени и огромным session id. Все они должны давать отказ, настоящие образцы без изменений разбираются.

## Как это проверяется

1. `tools/engine_ref.py` содержит эталонную реализацию на Python и проверяет инварианты на всех настоящих ClientHello из `vendor/zapret/bin`:
   сегменты данных вместе покрывают пакет ровно один раз, `fake` всегда первый, `multidisorder` даёт обратный порядок, перекрытие только у первого сегмента.
2. Он же создаёт `tests/engine-golden.json`: ожидаемые результаты (позиции разреза и планы всех правил YouTube) в канонической текстовой записи.
3. `app/native/NormaEngine.cs` повторяет ту же логику на C# (компилируется при запуске через `Add-Type`). Самопроверка NORMA (`tools/selftest.ps1`, в том числе в CI на Windows)
   сверяет C# с золотым файлом по каждому случаю и отдельно проверяет, что план, построенный из модели стратегии (`app/core/model.ps1`), совпадает с эталоном.

Каноническая запись плана: пакеты через `;` в виде `вид:смещение:длина:доп` (у `fake` доп это число повторов, у `data` перекрытие), затем `|U:` и список неподдерживаемого, затем `|F:` и тип подделки.
Пример: `fake:0:0:11;data:132:549:0;data:1:131:0;data:0:1:0|F:ts`.

## Сборка пакетов

Планировщик решает, какие пакеты отправить; сборщик (`PacketBuilder`) делает из решения настоящие байты IPv4+TCP на основе исходного пакета с ClientHello.

| Что | Как собирается |
|---|---|
| сегмент данных | заголовки исходного пакета; порядковый номер = исходный плюс смещение сегмента; длины и обе контрольные суммы пересчитываются; PSH остаётся только у сегмента, которым заканчиваются данные |
| перекрытие `seqovl` | перед содержимым первого сегмента идут N байт шаблона (`dpi-desync-split-seqovl-pattern`, при нехватке нули), порядковый номер сдвинут назад на N |
| поддельный пакет | те же адреса, порты и номера, что у исходного; содержимое из `dpi-desync-fake-tls` (файл, `0x...` или встроенный образец для www.google.com); повторов столько, сколько указано |
| `badsum` | контрольная сумма TCP намеренно неверна (увеличена на 1), сумма IP верна |
| `badseq` | порядковый номер сдвинут на `dpi-desync-badseq-increment` (по умолчанию -10000) |
| `md5sig` | в заголовок TCP добавлена опция MD5 (вид 19, длина 18, 16 нулевых байт), выравнивание NOP; не помещается: не применяется, отмечается |
| `ts` | TSval в опции Timestamps уменьшен на 600000; опции нет: не применяется, отмечается |
| TTL | `dpi-desync-ttl` для поддельных пакетов (иначе как у исходного) |
| идентификатор IP | с `ip-id=zero` у всех собранных пакетов 0, иначе ID исходного плюс номер пакета в плане |

Это определения NORMA: они делают сборку воспроизводимой и проверяемой, но не обязаны совпадать с `winws` в деталях (например, точное значение сдвига метки времени).
Не моделируются изменения поддельного ClientHello (`dpi-desync-fake-tls-mod`: `rnd`, `dupsid`, `sni=`), они отмечаются в результате; IPv6 пока не поддерживается.

Проверка устроена так же, как у планировщика: эталон на Python (`tools/packet_ref.py`), золотой файл `tests/packet-golden.json` (SHA-256 каждого собранного пакета для всех правил YouTube,
двух образцов ClientHello и двух видов заголовков, плюс отдельные случаи подделок), самопроверка на Windows сверяет C# с ним байт в байт и отдельно сверяет пакеты, собранные из модели стратегии.
Независимые инварианты (`python tools/packet_ref.py check`): верные контрольные суммы (кроме намеренно неверных), согласованные длины, склейка сегментов даёт исходные данные, PSH ровно у одного сегмента,
число поддельных пакетов, нужные опции в заголовке. Контрольная сумма проверена по известному примеру из описания IPv4.

## Как расширять

Новый приём добавляется сразу в две реализации (`tools/engine_ref.py` и `app/native/NormaEngine.cs`), затем:

```
python tools/engine_ref.py golden    # пересоздать золотой файл планировщика
python tools/engine_ref.py check     # инварианты планировщика
python tools/packet_ref.py golden    # пересоздать золотой файл сборки пакетов
python tools/packet_ref.py check     # инварианты сборки
```

В CI расхождение между реализациями или устаревший золотой файл покажутся красной проверкой. Меню «Дополнительно», «Разобрать стратегию» показывает план любой стратегии на образце ClientHello.

## Что дальше по этой линии

Отправка собранных пакетов через WinDivert в правильном порядке и с нужными паузами, перехват исходного пакета с ClientHello и подстановка в него плана вместо исходного пакета.
Планировщик определяет, что отправлять, сборщик создаёт байты; остаётся научить движок исполнять план на живом соединении и сверять результат со стратегиями `winws`.
